# B0 BF16 比 B0 FP32 慢：原因与受控复测

## 结论

此前 arxiv-10808269 的 BF16 B0 168.69 ms、FP32 B0 102.12 ms，主要受**两条路径不同的 NUMA 内存分配**影响，不能据此判断 AMX 比 FP32 慢。

在原节点 qhcn059、相同 CPU 44–59、相同三层 GAT、相同随机参数 seed=11 下，统一 NUMA 交错分配后：

| 内存策略 | FP32 B0 两个独立进程的中位数 ms | BF16 B0 两个独立进程的中位数 ms |
|---|---:|---:|
| 原初始化，FP32 页在 N6，BF16 页在 N5 | 103.275 / 102.360 | 167.874 / 169.907 |
| 先初始化 OpenMP，两者页都在 N5 | 157.599 / 157.371 | 175.013 / 173.767 |
| 两者强制绑定内存 N6 | 105.014 / 105.011 | 105.839 / 105.769 |
| 两者在 N5/N6/N7 交错分配 | 73.810 / 74.307 | 68.262 / 68.630 |

交错分配下，FP32/BF16 的平均进程中位数之比约 **1.082×**。这属于共享节点探索结果，不是论文性能验收结果。

## 原因链条

1. `prepare()` 在 BF16 路径中调用 `convert()`，其 OpenMP 并行区提前启动线程池；FP32 路径不转换权重，尚未启动线程池。
2. `OMP_PROC_BIND=close`、`OMP_PLACES=cores` 使 OpenMP 主线程绑定到 CPU 44。诊断日志中 BF16 在 prepare 前可运行于其它核，prepare 后稳定为 44。
3. CPU 44 位于 NUMA 5。之后 `Workspace::allocate()` 的 `vector.resize()` 在主线程串行初始化大缓冲区，按 first-touch 分配内存页。
4. FP32 进程在分配前尚未被 OpenMP 绑定，本轮位于 NUMA 6；缓冲区因此落在 N6。`/proc/self/numa_maps` 证实包含 Z/out 的大匿名映射：原 FP32 的页面均在 N6，原 BF16 均在 N5。
5. CPU 44–59 虽在同一 socket，却分布于 N5 的 4 个核、N6 的 8 个核、N7 的 4 个核。**绑定一个 socket 并不保证内存分配一致。** 两条路径的大数据访问集中于不同内存域，并承受不同的远端访问和共享节点竞争。

只调整初始化顺序就使 FP32 从约 102–103 ms 变成约 157 ms；无需执行 BF16 GEMM，也会复现相同 FP32 阶段的变慢。再用相同显式内存策略，阶段差异消失。这些对照共同支持 NUMA 是主要原因；没有把未经测量的 AMX 降频当成结论。

## 第二层逐阶段复测

以下来自交错分配的 AB 第一组进程，各为 3 次预热、9 次测量的阶段中位数，单位 ms：

| 阶段 | FP32 B0 | BF16 B0 |
|---|---:|---:|
| FP32→BF16 RNE | 0 | 1.268 |
| HW 投影 | 10.183 | 4.429 |
| L/R | 1.281 | 1.303 |
| row max prescan | 0.697 | 0.685 |
| score/exp/加权聚合 | 20.428 | 20.357 |
| normalization | 1.284 | 1.255 |
| ELU | 1.436 | 1.426 |
| layer total | 35.283 | 30.873 |

BF16 投影节省约 5.75 ms，转换增加约 1.27 ms。其它步骤继续使用 FP32 数据和相同 AVX-512 内核，基本等速。BF16 加速仅覆盖投影部分，因此三层端到端收益约 8%，不会等于 GEMM 的加速倍数。第二层 score/exp/聚合现在约占 BF16 层时间 66%，是更大的优化目标。

同绑 N6 时，转换约为 10 ms/三层，几乎抵消投影收益，端到端约持平；这也是测量内存策略必须明确的原因。

## 实验与验证

- build-20260930-161352：仅新增初始化和诊断选项，数学内核不变，编译成功。
- diagnose-10809043：qhcn025，申请 16 核但同一 socket 实得 10 核（22–31）；BF16 约 124 ms，FP32 约 134 ms。保留为补充，不能当作原 16 核对照。
- diagnose-10809069：qhcn059，16 核 44–59，原初始化与统一线程池初始化对照。
- diagnose-10809096：qhcn059，同一 16 核，`numactl --membind=6` 与 `--interleave=5,6,7` 对照。
- 每组按 FP32/BF16/BF16/FP32 的 ABBA 顺序，独立进程各 3 次预热、9 次测量，计时范围为完整三层 forward，不含图读取、静态准备、检查和输出。
- 数据 ogbn-arxiv：N=169343，E=2484941；预处理图、self-loop、三层结构、ELU、随机参数一致。
- 各次实验前运行边界正确性回归，均通过；全部 forward 输出有限。
- diagnose-10809096 两种内存策略、两次独立进程的**同精度**输出 SHA256 完全一致。BF16 与 FP32 相互不是同精度，不要求二者哈希相同。真实训练参数与任务精度验收仍待补充。
- 原始日志、页位置、线程 CPU、源码/二进制/图和规则哈希保存在 `baseline/runs/diagnose-*`。`source.sha256` 以服务端实验当时状态为准。

## 修正

`scripts/arxiv_payload.sh` 现在在任何 benchmark 子进程分配张量之前，对实际 CPU 集合涉及的 NUMA 域统一执行显式 interleave；缺少 numactl 或执行失败会停止，避免静默退回不同的 first-touch 策略。原始默认初始化和原日志保留，以便复现问题。

过去 arxiv-10808269 的 B0 FP32/BF16 相对性能结论应撤回；B1 对 B0 的比较也需在统一策略后重新测量。本文的新结果只回答 B0 变慢的原因，不用旧 B1 数字计算新的 TFS 加速比。
